# 顺序 3 失败原因与 Codex 源码对照

日期：2026-10-30。范围：分析 W02、W03，核查官方 `openai/codex` 的现成处理方式，提出待审核方案；未修改业务代码、配置、测试、评分或既有验收结果。

本次固定核查提交：[`f752c97f7d0be0cbef5cece327f52a16ad6fb1c6`](https://github.com/openai/codex/commit/f752c97f7d0be0cbef5cece327f52a16ad6fb1c6)。仓库内依据为[四题结果](../../eval/web-reader-step-3-web-results.json)、[验收报告](../implementation/web-reader-step-3-report.md)和[W02 离线预算分析](../implementation/evidence/web-reader-step-3-w02-budget-analysis.json)。

## 1. 结论

本轮主要故障发生在“取得网页之后如何定位、装入证据”和“最终回答如何约束归因”两处。六次网页请求均成功，W02 的完整快照已有两个参数定义，因此不能把这次失败继续归因为网络搜索不到或 TLS。

Codex 有可以借鉴的命令协议、输出限额、截断与来源保留机制；本次查到的开源路径并未提供可直接移植的网页抽取/定义排序引擎，也未发现能保证 W03 被拦截的事实语义校验器。下面明确区分已公开实现与本项目的设计建议。

## 2. W02：多层规则叠加导致有正文仍拒答

### 2.1 定位与裁剪均偏向开头

官方页快照为 16298 字符，`search_depth` 定义起于 4246，`include_answer` 定义起于 8866。实际送给模型的正文只有 `[0,182)`，主要是 SDK 示例。

`WebPage.window()` 保护代码块边界；`clip_source()` 遇到裁剪点落在代码块中就回退到代码块开头。`focus_source()` 对网页直接调用这种前缀裁剪，没有围绕本题参数定义选择正文。因此首次读取即使取得了更大窗口，装入模型时也会退回开头 182 字符。保护代码完整性本身合理，但“原文代码必须完整”和“所有网页任务都优先装下开头代码”不应绑定。

`WebRegistry.find()` 虽返回最多十个位置，却固定把第一个命中扩成正文。`search_depth` 首次出现在响应 JSON 示例的 1817，而非定义段的 4246；回退到完整代码起点后，候选正文是 `[182,5182)`。系统把本来可用于导航的查找操作绑定成了一次较大的正文输出。

定位：[窗口与 find](../../ai-service/internal/biz/web_sources.py)、[前缀裁剪与装包](../../ai-service/internal/biz/materials.py)。

### 2.2 人工分配阈值比真实请求上限更紧

`RAGBiz._fit_result()` 先从 16000 输入限额扣掉 2048 输出限额，再只允许新材料占剩余空间的一半。此次空结果基线估算为 10416，内部上限为 12184，新材料余量 1768 字节；保留第一个完整代码块及其元数据至少需要约 2371 字节，完整请求估算达到 12787，因此被拒绝。

之前从保存轨迹重建的最小原生探索请求估算为 15677，仍小于 16000；它没有真正发送，不能声称发送后一定能答对。可以确认的是：此次拒绝由内部材料分配阈值触发，不能解释成实际工具次数用完。

还有预算口径不一致：`InputBudget` 将输入限额、输出限额和模型总上下文容量分开定义，普通资料准备按 `min(input_limit, context_capacity-output)` 限制输入；这里却额外从输入限额再次扣输出，并在外层为最终回答预留消费预算。应统一计算各自限制，不能直接把 UTF-8 字节估算与供应商实际 token 当成同一量。

定位：[完整请求与材料预算](../../ai-service/internal/biz/rag.py)、[InputBudget 与 prepare_sources](../../ai-service/internal/biz/materials.py)。

### 2.3 装不下正文，连定位信息也被丢掉并立即收尾

`_fit_result()` 在原候选有正文、裁剪后正文为空且没有目录时返回 `None`，没有把有价值的 `matches` 作为可保留的独立结果。循环随后将整项替换为 `INPUT_BUDGET_EXCEEDED`，设置 `input_budget` 并结束探索。模型既没看到参数定义，也没看到后续命中位置。

本题最终只用了 3/10 次工具、4/6 次模型和 10561/64000 实际词元。拒答却称“工具调用预算限制”。`_denied()` 只写“程序已停止新增工具动作”，最终控制提示也没有提供可供准确解释的具体停止事实。应由程序传递和呈现实际停止原因。

若将 find 改成轻量导航，还必须同时调整两个地方：工具状态计算目前不把 `matches` 算成功结果；循环 `no_progress` 目前只认正文或目录，连续两次有新命中的查找可能被误判为无进展。只修改 find 返回内容不够。

本次零网络、零模型调用的离线复核再次确认：原 find 取到 `[182,5182)`；初始窗口裁到 1000 字符时回退到 182；find 窗口裁到最小前缀时为空；定义段附近的独立小窗口可正常从同一快照读取。预算数值沿用保存轨迹的重建结果，没有追加真实问答。

## 3. W03：已有引用约束，但没有逐项落实

模型前文已经正确承认官方片段没有直接定义镜像，末段却又称两类资料都“隐含或明示了镜像作为基础的角色”，且该段没有引用。问题是把一个来源的结论扩大归因给两个来源，不宜据此说整道回答全部错误。

现有提示已经要求每个事实段落附引用，并只根据送模正文回答；再重复一遍同类提示不足以解决该缺口。`_publish()` 目前检查 JSON、引用编号、回答至少有一个引用、摘要与正文类型，以及围栏代码是否有原样依据；不要求每个事实段落有引用，也不验证引用内容是否支持断言。保存事件明确写 `semantic_support=not_evaluated`，因此 `answer_validated` 不等于语义验收通过。

W03 也因 `input_budget` 被程序收尾，没有显式 `finish_research`。这说明它受到相同材料预算影响，但不足以证明预算就是末段错误归因的直接原因。归因越界与校验缺口需要独立处理。

定位：[生成约束](../../ai-service/internal/prompt/templates/rag.yaml)、[最终发布校验](../../ai-service/internal/biz/rag.py)。

## 5. 建议的修复顺序（尚未实施）

1. **先修证据导航。** find 的唯一职责改为返回有界的命中目录：原文位置、短预览、所在段落/是否代码；由模型选择具体命中，用现有 read 在同次快照读取小窗口。明确区分导航预览与可引用正文，不能把未登记预览当证据。支持一次查找两个参数、一次读取两个所选窗口，减少模型往返；按新增位置判定进展。不得为 Tavily 参数硬编码偏移或关键词排序特例。
2. **再统一材料预算与停止原因。** 保留当前单次输入、输出、总词元、次数和时间限制，取消固定一半分配及不一致的重复扣减；每次按完整原生请求核算探索和最终收尾是否都可执行。正文按所选原文段落装入，所需代码块完整保留；无关代码不强制随定义送模。导航结果与正文预算分别有界，某个正文窗口无法容纳时应如实报告该窗口限制；仅在完整请求、总预算或其他真实终止条件满足时收尾。所有操作仍走原有授权来源和快照路径，不增加备用抓取、静默重试或第二套工具链。
3. **再收紧最终回答归因。** 最终结构将事实条目与引用编号绑定，由程序渲染引用，防止游离的无引用事实段；多来源对比拆开表达，各自对应证据。声称“两者都支持”的结论必须提供两边的依据，缺少一边时表达为“本次官方片段未覆盖”，不能自行归并成共识。结构校验只能保证字段和引用关系，不能保证语义蕴含；即使添加原文摘录核验，也须明确这一限制。若要求自动语义门禁，需另外设计和验证，不能谎称 Codex 已有可搬模块，也不能擅自追加一个无限额模型审查调用。
4. **最后做少量针对性验收。** 待用户授权实施后，先用现有快照检查定义定位、装包及引用结构，再各跑一次 W02、W03。只有相关改动可能影响代码提取时才补一题 W01；不通过时保留真实结果，不反复重跑追求通过。

以上是针对失败模式的通用方案。其中文页导航、定义段选择和最终归因控制需要自行实现；不能包装成直接移植 Codex 的完整解决方案。本次未实施任何一项。

## 6. 评分旁支问题

现有关键词指标把 W02 拒答中出现两个参数名也记为命中，产生“正确率 100%”的误导。它未导致运行时拒答，但会掩盖质量问题。应单独修正指标的状态前提，并继续区分结构通过、正确作答和原文支撑；本次保持旧评分及验收结果原样。
