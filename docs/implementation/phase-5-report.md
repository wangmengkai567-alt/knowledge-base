## 已交付行为

1. 文档持久化四个阶段：解析、分块、向量索引、关键词索引。每个阶段分别保存 pending/running/completed/failed/skipped、错误和更新时间。原 status 字段继续仅表示解析状态；新增 ingestion_status 汇总入库状态。
2. 解析、分块、向量全部完成，且混合检索所需的关键词索引也完成，才返回 ready。纯向量配置明确将关键词阶段标记为 skipped。未就绪文档不作为当前检索资料；重解析尚未完成时，当前分块接口不暴露保留的旧分块。
3. IngestionBiz 统一编排阶段与同文档互斥；删除、重新解析和重试共用文档锁，避免并发替换或删除后继续入库。阶段异常和取消都有独立记录，不再吞掉分块或关键词错误，也不以向量检索掩盖混合索引失败。
4. 向量按批记录成功与失败。重试前核对真实向量及文档、知识库归属，只请求仍缺失的分块，保留已成功的批次和已有失败统计。没有更换向量模型、维度或默认重新嵌入存量资料。
5. 关键词建立独立于嵌入；关键词失败不把已成功向量改成失败。单独重试关键词会重新索引当前全部分块并核对实际覆盖，不调用嵌入模型。
6. 启动时保留当前解析、分块阶段的完成标记，只核实已确认完成阶段的正文、分块和真实向量，再重建当前进程的关键词索引。pending/failed 不因旧资料仍存在而升级完成；running 转为中断失败。缺失向量、关键词重建失败会记录到对应文档；无法读取清单、保存状态或缺少显式迁移时阻止开始服务。当前 PostgreSQL 配置不会在启动时重新生成向量。
7. 前端列表依据完整阶段显示入库完成、具体失败阶段或处理中，向量数量显示实际完成数。详情页逐阶段展示错误、更新时间和重试入口；只有全部必需阶段完成才提示成功。重新解析与从失败阶段继续是两个明确操作。
8. 删除旧的 /embed 路由及前端调用，统一使用 POST /api/v1/knowledge/bases/{kb_id}/documents/{doc_id}/retry。空对象从失败或待处理阶段继续；stage 可显式指定 parse、chunk、vector、keyword。前置解析或分块未完成时拒绝索引重试；已解析文档重新解析仍使用 /parse 与 force=true。限流分类和接口说明同步更新。

## 重新解析与引用

重新解析先撤销就绪状态并清除旧解析正文。解析失败时保留原文件、旧分块及旧索引，文档保持失败且不参与召回；界面明确说明保留的旧分块等待替换。

取得新文本并成功生成分块后，先清理旧向量和关键词，再在同一数据库事务中分配新分块编号、删除旧分块并提交。事务失败保留旧分块，但文档仍失败且不可召回；重试从分块继续。新分块保存后，向量和关键词分别建立、分别记录失败。先分配新编号也避免 SQLite 在本次替换时复用旧编号。

已经进入问答运行的来源快照保留其当时实际内容；后续重解析不改写这些快照。旧引用跳转找不到当前分块时，沿用第四阶段的明确提示。

## 第一项缺陷修复（2026-10-29）

复查发现：重新解析已经提交新正文与解析完成状态，但尚未替换分块时中断，原启动代码会根据旧分块连续、非空以及旧向量仍存在，把新轮次错误发布为 ready。

先实际读取既有参考项目的固定版本源码，再采用 RAGFlow 的“当前解析轮次状态为权威、历史任务不代表当前轮次完成”，以及 Onyx 的“确认索引写成功后才提交新分块数量/内容标记”原则。本地当前 stages 就是唯一当前处理轮次；分块完成标记只由实际替换完成的处理路径产生。没有引入它们的队列、框架、多工作进程或通用工作流。完整路径、函数、行号与其他项目不适用的原因见[专项源码调研](../research/phase-5-reparse-consistency.md)。

修复限于 ingestion.py 与 ingestion_migration.py：启动不再将当前 parse/chunk 的 pending/failed 升为 completed；running 记录中断，已 completed 的阶段仍需核实实际产物。无阶段的旧系统资料改由显式迁移核实，启动缺少迁移时明确拒绝，避免把首次存量核实与新处理轮次恢复混用。

同一临时命令使用真实 process(force=True)、SQLite 仓储、内存向量和关键词，在解析完成落库后模拟进程终止。修复前输出 NEW 正文、OLD 分块、ready，目标断言失败；修复后输出 NEW 正文、OLD 分块、pending，关键词未登记旧块、嵌入调用为零。定向分块重试后才发布 NEW 新编号分块，解析累计一次、嵌入一次；再次启动维持 ready，嵌入调用不增加。

另外核查 parse/chunk 各自 pending、running、failed 共六种启动边界；无阶段旧结构迁移及重复执行、现代 pending 不被迁移覆盖、缺少迁移时拒绝启动均通过。未新增或修改测试、评测文件；检查命令没有保存为脚本文件。

实际容器中显式迁移与后端重启成功，就绪检查 HTTP 200；29 篇文档四阶段均完成，仍为 6 个知识库、29 篇文档、1153 个分块和 1153 条向量，向量内容及元数据整体指纹与修复前一致。源码编译、两个修改模块 Ruff 和 git diff --check 通过。

本轮仅修复第一项问题。审查中的旧索引挤占候选、完成状态落库取消窗口及详情页旧分块计数问题仍未纳入本次修改。

## 第二项缺陷修复（2026-10-29）

未就绪文档保留的旧分块原先参与向量与 BM25 排名，占满各路候选后才在 RetrievalBiz 被排除，可能导致就绪文档无法召回。临时命令使用 80 个未就绪旧分块和 1 个就绪分块，真实纯向量、混合检索在修复前均返回空列表，修复后均返回就绪分块。

先实际读取六个既有参考项目的固定版本源码，直接采用 RAGFlow 和 Onyx 的“资格条件进入每个召回分支，先过滤再截断”处理方式；Open Notebook 的父文档范围预先解析和 Khoj 的查询过滤顺序提供进一步核实。实际源码入口、行号及适用边界见[第二项专项调研](../research/phase-5-retrieval-eligibility.md)。

RetrievalBiz 在查询前读取当前知识库的 ready 文档范围，以独立 document_ids 参数传给所有查询变体及向量、关键词分支。存储层在候选评分和 top-k 前限定范围；None 表示未限定，空列表表示没有候选，并与原知识库元数据条件取交集。出口仍复核最新文档状态，拒绝执行期间已撤销就绪的资料。没有新增扩大候选、循环补召回或备用路径，旧索引仍保留供原有重试使用。

PostgreSQL 对合格集合先 MATERIALIZED 再精确余弦排序，避免 HNSW 扫描后的过滤继续耗尽有限候选。这是当前规模下明确选择的精确检索路径；候选集增大时，计算和内存成本也随之增加，不声称其具备近似索引的大规模性能。现有知识库 8 篇就绪文档的查询抽查 10 次，中位 5.02 毫秒、最大 15.82 毫秒，仅代表当前规模。

真实 SQLite 仓储核查两种检索器、四阶段 pending/running/failed 共 24 种状态组合；空范围不请求嵌入、跨库隔离、未知文档、关键词 skipped、多查询变体透传及检索期间撤销就绪均通过。真实 PostgreSQL 临时表强制使用 HNSW、ef_search=1、iterative_scan=off 时，普通过滤查询返回空，修复后返回目标分块且余弦分 0.8；文档范围边界通过，临时表随事务回滚并确认不存在。

现有资料使用真实 PostgreSQL、仓储和新建内存 BM25 完成两种检索器的调用核查；使用已有向量作为查询，没有请求外部嵌入。仅重启 ai-service 后，health/ready 返回 200，1153 个分块完成关键词预热。仍为 6 个知识库、29 篇文档、1153 个分块、1153 条向量，29 篇全部就绪；正文、分块内容及向量和元数据的整体指纹与重启前完全相同。

七个修改的 Python 模块编译通过；与 HEAD 相同方式比较 Ruff，仍为三项已有诊断，零新增。交付前检查相关文件换行及 git diff --check。未新增或修改测试、评测文件，未新增依赖、修改数据结构或提交代码。第三、第四项审查问题仍待单独处理。
