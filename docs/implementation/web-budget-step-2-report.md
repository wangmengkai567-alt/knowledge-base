## 改动与原因

### 1. 输入、输出与总消费分别核算

`InputBudget.input_ceiling(output_tokens)` 成为资料准备、原生请求校验和运行规划共用的输入上限计算：`min(input_limit, context_capacity-output_tokens)`。不再把输出限额从独立的 16000 输入上限里重复扣除。

`RequestBudgetPlan` 同时计入完整的两种请求：

- 探索请求：当前提示、原生调用/结果消息对、所有工具定义及实际请求视图。
- 最终请求：当前正文与历史、严格 JSON Schema、程序提供的停止原因说明；没有工具定义。

继续探索时，总消费预留为“探索输入估算 + 本次输出上限 + 最终输入估算 + 最终输出上限”。这两次输出分别对应两次模型请求，不能作为重复扣款删除。实际消费仍由供应商用量结算，估算和预留不记成实际消耗。原因尚未确定时按最长的收尾控制消息预留，防止最后补充原因反而挤破边界。

上限保持：单次输入 16000、输出 2048、总实际用量 64000、最多 6 次模型/10 次工具、120 秒。仍使用原有保守 UTF-8 字节估算；它不等于供应商精确 token 数。

### 2. 整批装入实际元数据，再分配正文

删除“每份资料只占一半剩余输入空间”的规则。一个模型动作批次的工具结果统一装包，先计入全部调用结果的实际目录、命中、错误等元数据，避免前一段正文用满空间后，后一段连基本结构也放不下。

网页正文因预算缩短时在段落边界结束，并继续保护完整代码块，不能把几个字符当作可用证据。引用只登记实际送入下一次模型请求的原文范围；同一快照的重叠范围仍去重。

若只剩最终回答的额度，本批已取得的资料仍可按最终请求预算送入收尾，不为不存在的下一轮探索多留一份额度，也不直接丢掉最后一批可用正文。

### 3. 已消费导航使用较小的后续请求视图

完整流程回放显示，仅取消减半规则仍不够：模型选好位置后，旧 find 预览继续占用空间，会把定义正文挤掉。因此，后续 `web_read` 覆盖某次 find 的命中位置后，该次导航在后续请求中只保留全部匹配位置、来源编号、代码标记，并显式标记预览已省略。

未选择读取的其他查找保留完整预览，即使它们位于同一网页。所有原生调用/结果消息对、正文证据及其引用保持原样。原始导航预览保留在事件与快照中；这不是改写原始结果或为未读内容补造依据。估算与实际发送调用同一个请求投影方法，避免估算一份内容、实际又发另一份。

### 4. 单窗口限制不再误报为整个研究失败

原文窗口因输入空间无法保留时，向模型返回 `MATERIAL_WINDOW_TOO_LARGE`，明确该窗口未作为证据送模。代码块超过所选窗口上限等局部限制也可继续选择其他片段；模型必须显式调用同一套工具，不会自动重试、换抓取路径或扩大权限。

真实供应商失败、权限错误、未知用量、超时等仍按原有终止机制处理。连续没有新信息与重复动作的保护继续生效。

### 5. 程序准确传递和呈现停止原因

最终控制消息携带具体程序原因及解释，区分 `input_budget`、`token_budget`、模型次数、工具次数与证据不足。预算导致停止且最终仍无法作答时，运行状态为 `budget_exhausted`，保留实际原因，不再一律归为 `insufficient_material`。

界面同步展示完整请求输入限制、窗口限制和总额度不足。模型自身的自然语言解释仍可能出错，程序状态与界面原因是确定的；本项没有增加事实语义校验器，也未实施顺序 3 的最终归因改造。
