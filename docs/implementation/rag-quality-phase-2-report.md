## 2. 2A：统一参数与可定位错误

工具定义与实际执行继续共用 Pydantic 参数模型，去重检查和工具执行改为共用参数解析入口。关键词的每项 `minLength=1`、`maxLength=32`、单行非空白模式，以及数组 1—8 项和禁止额外字段均进入模型可见 Schema。连接各项时用一个空格，总长度最多 120 字符；组合限制写入工具说明，并由同一参数模型校验。

保留 32 / 120 的本地边界，没有将其说成 Tavily 的供应商限制。37 字符的英文短语确实可能被本地限制拦截；本次只显式表达和核对这项限制，没有授权或实施放宽。参数不再在校验前隐式裁剪空白或去重；Schema 针对的原始参数就是本地检查的参数，不用转换修复非法输入。

报错仅显示字段、约束类型与必要长度，不回显参数或额外字段原文。例如历史 W02 参数准确返回：`keywords.2: string_too_long (max_length=32, actual_length=37)`；连接后 123 字符返回 `keyword_total_length / actual_length=123 / max_length=120`。数组类型、整数字符串、额外字段和控制字符均明确拒绝。

最终正式工具定义统一请求 `function.strict=true`，线上只有这一种工具定义，不保留失败后改用非严格参数或改写参数的分支。服务是否兑现约束仍由真实结果判定。

## 3. 2B：有限能力检查与服务缺口

[固定能力矩阵](evidence/rag-quality-phase-2-capabilities.json)使用相同模型与主机、温度 0、输出上限 512，每种形态仅一次公开资料请求：

| 模式 | 实际观察 |
|---|---|
| 无工具的严格回答 Schema | HTTP 200；合法对象、字段与枚举符合要求，真实用量完整 |
| 原生工具 `auto` | HTTP 200；真实调用编号、参数、`tool_calls` 结束原因及用量一致 |
| 严格回答 Schema 与工具联用 | HTTP 200；返回原生调用及普通说明正文，未据此证明最终 JSON 契约稳定 |
| 原生工具 `required` | HTTP 200；确实返回工具调用，结束原因和用量一致 |

W02 在新 Schema 下仍生成 34 字符关键词，因此补充了一次[严格工具模式能力检查](evidence/rag-quality-phase-2-strict-tool-capability.json)：服务接受 `function.strict=true`，该固定请求的参数合法。随后正式工具定义采用严格模式，但真实 W02 又生成 37 字符关键词，证明“参数被接受、简单探针合法”不足以证明服务稳定遵守 Schema。

正式 W02 运行编号 `eac4f067-9757-4186-bd8e-71eb99038db1`，错误为 `keywords.2 / string_too_long / 37 > 32`。本地立即停止，未调用 Tavily，未重答或修复参数。这个失败仍是第 2 阶段工具参数契约问题，不能改称网页连接失败，也不能算作第 3 阶段搜索或正文读取验收。

后续服务端需要兑现原生工具 Schema 的长度约束，或明确报告不支持相关严格约束；应使用相同模型、原题和现有 Schema 验证。当前没有切换服务、删掉校验、截断关键词或扩大长度来制造通过。

## 4. 2C：唯一的两阶段生成协议

正式流程为原生工具探索，再进行无工具定义的严格最终生成：

- 首轮请求 `tool_choice=required`，先真实取证；如果服务未返回要求的原生调用，保留实际用量并明确失败。
- 后续探索可选择工具或结束。普通文本和工具描述均不作为已执行动作，也不发布或加入最终请求充当事实来源。
- 探索结束进入预先规划的最终生成，调用独立的 `generate_answer`；请求包含严格回答 Schema，不发送 `tools`、`tool_choice` 或工具并行参数。
- 最终 Schema 与本地业务字段解析共用 `AnswerPayload`，来源和引用范围检查继续执行。非法输出保持失败，不再追加格式修复请求。
- 探索与最终调用各自计入原 6 次上限、实际用量和总时限。收尾预留与材料预算按最终请求重新估算，包含严格回答 Schema 的空间。

API、SSE 与快照保留 v5 的既有字段契约；每个 `model_started` 事件新增明确的请求模式、工具定义数量和工具选择。评测增加两阶段协议核对；前端同步显示取证结束与格式或引用失败。旧结果不补造新事件、不重新评分写回。
