状态：第 0、1 阶段已执行，见[第 1 阶段实施记录](../implementation/rag-quality-phase-1-report.md)。第 2 阶段代码改造与小样本验证已执行，见[第 2 阶段实施记录](../implementation/rag-quality-phase-2-report.md)。后续按用户确认将单项关键词上限放宽至 64 字符，W02 成功搜索和读取网页，但后续生成 71 字符短语仍被拒绝，工具参数契约验收未通过，见[长度调整记录](../implementation/rag-quality-phase-2-keyword-limit-report.md)；第 3—5 阶段未执行。本文承接 [上一轮优化报告](../implementation/rag-quality-optimization-report.md)，不替代原重构计划或历史评测记录。

## 一、要解决的问题

本计划围绕四个问题展开：单题预算计量与收尾策略、结构化输出与工具约束、联网失败定位、跨库证据覆盖与压缩。目标是在保留真实来源和既定执行边界的前提下，提高正常回答和正确拒答的比例。

先澄清“重复计算预算”：

- 同一段历史每次重新发送给模型，确实会再次消耗词元，这部分必须按供应商报告累计。
- 当前缺陷是把保守字节估算作为长期扣减依据，而非在调用完成后按真实用量结算；多轮执行会累积估算偏差。
- 当前还会额外预留最大输入窗口与输出额度，并将部分合法收尾回答统一标为预算失败。这些问题应分别修正和评估。
- 因此，不能通过“相同文本永远只计一次”解决，也不能直接将整个验证轮次视为共享预算。累计预算始终属于一次问答运行。

制订本方案的原始轮次只创建方案；后续执行范围与真实结果分别保存在各阶段实施记录中。

## 三、共同约束和阶段顺序

继续使用当前配置的模型、服务地址、嵌入与重排模型、Docker 和已有数据。一次问答的模型调用最多 6 次、工具最多 10 次、总时限 120 秒、输出最多 2048 个词元、累计实际用量目标上限 64000 个词元，先不提高这些数值。

单次输入暂保留现有 16000 的保守预检阈值，明确它目前采用字节估算，不把它称为精确模型词元计数。是否引入精确计量，必须先核实当前模型对应的分词器或服务计量能力，不能套用未经验证的其他模型分词器。

工具始终限定在用户选择且有权访问的知识库及明确开启的联网范围。失败必须明确返回，不增加文本解析工具调用、自动补括号、非法参数转换、失败重答或供应商切换路径。删除被替代的实现，不保留两套线上预算或终态推断逻辑。

## 五、阶段 1：修正单题预算与收尾状态

### 1A：实际结算与预留分账

当前入账逻辑以“输入估算与实际输入的较大值＋实际输出”扣减。应替换为实际结算与调用前预留两个明确概念：

```text
单题已结算用量 = 所有已完成调用的实际输入词元 + 实际输出词元
单题剩余额度 = 64000 − 单题已结算用量
可用于新增探索的额度 = 剩余额度 − 正在持有的调用预留 − 收尾预留
```

实施要求：

1. 每次模型调用按运行编号与调用序号结算一次，避免开始、完成、快照保存等多个环节重复入账。
2. 累计结算只加实际输入和实际输出；接口的总词元字段用于核对，不再额外相加。重复发送的历史按每次真实输入累计，缓存命中也依照接口报告处理。
3. 请求发出前用输入估算和输出上限临时占用空间；返回后释放对应预留，以真实用量结算。估算单独留档，不留在实际已消耗用量里。
4. 收尾预留按当前已组织、压缩的最终请求计算，不固定持有“最大输入窗口＋最大输出”的最坏值。探索调用和收尾调用各自所需的额度仍须计算，不能漏掉其中一次。
5. 工具结果到达后重算剩余额度及可容纳资料。需要缩减材料时保留关键证据；无法保证收尾空间时停止新增探索。
6. 缺失用量、传输中断或取消后用量未知时，明确记录未知并停止继续执行。不能按零消耗记账，也不能声称已精确证明这次运行的实际总消耗。
7. 若供应商实际返回用量超过请求约束，完整记录已发生消耗并报告超限；不能丢弃、截小或伪装成正常完成。

A22 的诊断目标：历史记录的实际输入加输出为 12972，原扣减为 50908。新的离线账本复算应得到 12972，但不能据此把旧运行直接改成成功；新流程效果要通过重新执行确认。

### 1B：停止探索与答案状态分开

1. 分别记录“为何停止继续取证”和“最终回答的结果”，不要用一个停止原因同时表达两件事。
2. 接近预算、达到探索轮次或没有新证据，可以进入预先规划的最终回答阶段。该次调用仍包含在 6 次模型调用及累计预算内。
3. 最终回答通过结构、来源与引用检查，且没有真实硬预算超限、取消或依赖故障时，依据回答协议结束为正常完成或资料不足，同时保留停止探索的原因。
4. 没有额度执行收尾、实际用量超限、用量未知、无效输出、工具故障、超时及取消，继续保持各自明确的失败状态。
5. 通过结构和引用检查不等于事实正确；事实支撑与答题完整性仍单独评价。
6. API、过程事件、前端展示、保存快照及评测同步调整。同一阶段完成协议切换，清除被替代的线上逻辑。历史 JSON 保持只读，离线比较显式区分历史口径和新口径。

## 六、阶段 2：验证严格输出能力，统一工具约束

### 2A：统一工具 Schema 与本地校验

1. 用同一份参数定义生成模型看到的 Schema 和本地校验规则。类型、必填项、数组数量、数值范围、单项字符串长度和额外字段政策保持一致。
2. W02 的单项限制经用户于 2026-10-30 确认，由原定 32 字符放宽为 64 字符，总计仍为 120 字符。单项长度写入 Schema，总长度和其他不能直接由 Schema 表达的组合规则写入工具说明，并与服务端规则核对。
3. 本次调整用于减少合理英文搜索短语被误拦截；这是本地规则，不是 Tavily 的供应商限制。新旧结果分别保留，目的、验证及影响见[长度调整记录](../implementation/rag-quality-phase-2-keyword-limit-report.md)，不能据此证明服务稳定兑现所有 Schema 约束。
4. 校验失败记录具体字段与约束类型，例如“第 2 个关键词长 65，允许最多 64”，避免一律写成“类型错误”。不记录密钥或无关私有内容。

### 2B：验证当前服务，而非只验证参数被接受

当前代码已请求严格回答 Schema。本阶段解决的是服务是否兑现约束及阶段协议，不是再往提示词里多写一次“请输出 JSON”。

用固定、有限的能力检查区分：

| 请求形态 | 核查什么 |
|---|---|
| 不携带工具的严格回答 Schema | 是否为合法对象、字段与枚举是否符合约束 |
| 原生工具调用 | 调用编号、名称、参数、结束原因及真实用量是否一致 |
| 严格回答 Schema 与工具联用 | 是否出现忽略约束、普通文本工具描述或不一致结束原因 |

记录模型名、服务主机、模式、请求上限、实际响应类型、用量、耗时和失败。探针成功后仍须用原来的 9 道无效输出题及 8 道未取证就结束的题验证，不能用单个简单示例证明稳定支持。

### 2C：确定唯一的正式阶段协议

优先验证“原生工具探索 → 无工具定义的严格最终生成”两个明确阶段。最终生成调用在执行前预先规划并计入预算，不是在坏输出后临时追加格式修复请求。

探索阶段不得把普通文本里的工具描述当作已执行调用。最终阶段继续检查业务字段、实际来源和引用范围。若当前服务无法稳定支持必需模式，记录能力缺口及服务端修复要求；不能靠删掉校验、文本兜底或静默换服务通过本阶段。

## 七、阶段 3：拆开联网故障，验证真实读取

### 当前事实

W04 已实际搜索成功。W01、W03 的正文读取出现 HTTP 连接或传输异常，均约 3.3 秒，未被客户端识别为超时。W02 被本地长度校验拦截，未请求供应商。不能把这三类问题统一说成“联网工具不能用”。

### 工作内容

1. 保留异常类型与发生阶段，区分连接失败、TLS、读响应或连接中断、客户端超时、供应商 HTTP 状态错误、供应商逐网址提取失败、空正文和响应格式错误。
2. 记录端点类型、耗时、HTTP 状态及适当的请求追踪标识；不保存授权头、密钥和完整私有提示。对没拿到响应的情况，不编造 HTTP 状态。
3. 分开验证搜索端点与正文提取端点。搜索成功不代表正文读取成功，收到 HTTP 200 也不代表取得了题目所需内容。
4. 用 W01、W03 的原网址及固定公开搜索主题重现。依据明确异常再修复连接、代理、证书、超时层级或请求构造；不盲目增加等待时间。
5. 同步核对客户端超时、供应商提取超时和单题 120 秒总时限，避免内外层限制相互冲突。
6. 保持只读和网址授权范围，不增加失败后的供应商切换、直接抓取备用通道或自动重试。

## 八、阶段 4：跨库证据覆盖与问题相关压缩

### 4A：先做不额外调用模型的原文抽取

1. 从当前问题列出需要回答的子问题，按已授权知识库和文档组织取得的证据，记录哪些部分已覆盖、哪些仍缺失。
2. 优先保留与问题直接相关的命中原文及必要邻近句段。比较题保留数值、单位、适用条件、否定词、文档身份和时间，避免把不同来源拼成同一配置。
3. 继续去除已提供的重复范围，压缩无关背景与冗余记录；不再靠资料列表顺序分配全部空间。不能把来源列表中的每份文档都概括一遍，替代证据选择。
4. 结合阶段 1 的实际剩余额度，动态确定证据空间和收尾空间，不只使用固定的“一半”比例。
5. 为缺失子问题检索所需的不同证据；已有证据足够时直接进入最终生成，不为确认已知结论继续搜索。
6. 所有保留片段仍对应原始分块、字符范围和文档版本。摘要或抽取结果不是新的独立事实来源。

### 4B：必要时再做生成式摘要的受控比较

只有在原文抽取后，仍因长材料或多轮重复输入而受限时，才开展摘要实验：

- 摘要必须面向当前子问题，按来源分别生成，显式保留关键数值、单位、条件、否定和冲突，不能只留通用介绍。
- 摘要调用、输入输出、耗时和资料空间全部计入同一次问答的 6 次模型调用、64000 实际词元及总时限内。
- 同题比较原文抽取与摘要两个候选方案，分别记录最终请求大小、单题累计用量、证据保留、答案正确性与来源定位。
- 必须验证摘要中的重要结论可回到真实原文，最终引用不只指向摘要。不能把压缩后遗漏的事实视为原文不存在。
- 只有总体收益成立才采用摘要。实验结束后选择一套正式策略，移除未采用的生产实现，不保留“失败就换另一种”的运行路径。

摘要可能缩小最终请求，却增加整题消耗；本阶段以整题收益为准，不预设摘要一定更好。

### 预期涉及位置

`ai-service/internal/biz/materials.py`、`rag.py`、`tools.py`，以及来源 DTO、运行记录与评测中的证据覆盖项。只有摘要方案被正式采用时，才增加相应的模型阶段与调用统计。

### 验证与完成标准

- 优先验证 CROSS01、F01 及原有多来源题。CROSS01 应实际使用两个已授权知识库，取得 Docker 与安全文档的相应原文，分清两套配置并正确引用。
- F03 继续保留历史单库范围，不能为了达标把它改成双库题。历史题范围限制和 CROSS01 的执行能力单独报告。
- 不凭更少字符认定改进，必须同时核对证据完整性、真实用量及最终回答。
- 正式压缩策略确定后执行完整 100 题、4 道联网题及跨库场景，确认局部压缩没有损害其他问题。若之后又改变正式策略，需重新验证其直接影响范围。

## 九、阶段 5：统一验收和结果留档

### 必须保留的比较

每个阶段保存明确命名的结果、配置与原因记录，文件名不附加哈希。运行编号、代码版本或内容摘要作为记录字段保存。至少并列以下三组结果：

1. 本计划开始前的 65.56%／1.33% 完整基线。
2. 各阶段新实测，特别是预算计量、终态分类、输出协议、压缩策略的变化。
3. 原历史质量参照：按同一补词标准为 94.44% 正确率，归档疑点率 1.11%，拒答正确率 100%。历史缺少同协议快照的限制继续说明。

终态改变导致的重分类，使用同一份保存答案单独计算其影响；实际重跑导致的内容与行为变化另列。不能重写旧快照，把它伪装成新流程的成功证据。

### 验收指标

| 维度 | 必须记录或满足的要求 |
|---|---|
| 单题账本 | 实际输入输出可核对，估算与预留分开；每次调用只结算一次；未知量未当零 |
| 执行边界 | 模型、工具、时间、输入输出上限遵守约定；每题单独计量，整轮用量另汇总 |
| 正常完成与拒答 | 成功、资料不足、故障和超限区分；拒答目标保持 100% |
| 回答质量 | 同标准与 65.56% 基线比较，最终以恢复历史 94.44% 为目标；所有退步题单列 |
| 幻觉疑点 | 保留原规则与 1.11% 历史目标；所有疑点核对实际来源，不能通过临时改规则压低数值 |
| 联网与跨库 | 4 道联网题和 CROSS01 真实执行，全部按场景要求核对；保留失败及其具体原因 |
| 原文与引用 | 所有实际送模片段、文档版本、字符范围和引用映射审计通过 |
| 压缩收益 | 同时比较最终输入、整题累计用量、证据保留与质量；摘要额外调用不漏计 |
| 资源与稳定性 | 模型/工具调用、输入输出、未知用量、延迟中位数/高分位/最大值均列出 |

自动正确率不是独立人工语义评级，疑点率也不是已确认幻觉比例。预算停止、引用冲突、跨来源结论、全部自动疑点和回归题须做有范围说明的语义复核。因已知误报未过自动门槛时，保留未通过结论并解释，不自动宣布总体通过。

最终实现已被最近一轮完整评测覆盖、配置与规则未变时，复用该轮作为最终结果，补齐来源审计与比较即可；不为“最后再验收一次”重复消耗整轮模型。只有实际改动、失败或覆盖不足才追加实测。单轮对比和小样本探针不能被称作统计稳定性证明。

### 验证方式与项目规则

运行现有检查、保存答案的离线分析、临时诊断和必要的真实接口实测。Python 环境与依赖使用 uv。本计划不授权新增或修改测试文件；若现有检查断言的是被替代的旧终态，应在阶段记录中指出冲突和涉及范围，不能隐藏失败、偷偷改期望或为绿灯恢复错误行为。

每阶段记录改动、原因、已运行检查、逐题差异、资源消耗和未解决项。检查相关文件编码及换行，运行 `git diff --check`。不自动提交、推送或归一化现有 Git 改动。

交付预算与协议说明、每阶段实施记录、完整结果及逐题对照、语义与来源审计、用量汇总、联网/跨库记录、明确的通过和未通过项。没有真实结果的阶段保持“未执行”；未达质量目标时据实记录，不把方案、探针成功或代码检查通过当作最终质量恢复。
