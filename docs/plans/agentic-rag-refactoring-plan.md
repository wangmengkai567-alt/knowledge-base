# 个人知识库扩展为智能体检索问答：分阶段重构计划书

日期：2026-10-27

状态：准备阶段、第一阶段、第二阶段、第三阶段已完成；第四至第六阶段尚未开始（2026-10-28）

项目：AI Knowledge Base

## 一、目标与已经确认的范围

在现有 Python FastAPI + Vue 3 项目上重构，使一次提问可以由后端自主选择知识库检索、网页搜索、网页读取和明确批准的外部只读工具，依据实际取得的资料形成答案。

用户已经确认：

1. 保留 Docker，重构初期继续通过容器运行后端、PostgreSQL 与 Redis；前端开发仍可在本机进行。
2. 修复按分块顺序重新制造分数的问题，统一资料筛选、来源追踪、上下文预算和引用映射。
3. 允许后端管理工具执行循环、运行状态和过程展示。
4. 回答中的事实性结论必须有实际使用的来源支持。
5. 完善现有入库状态，保留已经实现的失败记录和针对失败步骤的重试能力。
6. 完整效果评估与最终验收放在最后；实施中保留必要的功能检查。
7. 可以添加术语表和已确认的设计决策记录。添加文档不等于立即提交或推送 GitHub。
8. 保留现有 GitHub 参考调研文档，并在 docs 中新增本计划书。

准备阶段的实际完成记录见 [准备报告](../preparation/preparation-report.md)。已完成成对备份、环境启动、配置核对及关键选型；未执行第一阶段业务重构或自动提交。

## 二、第一版的功能边界

### 要交付的结果

- 后端负责完整问答，浏览器不再挑选生成所用分块或提前决定拒答。
- 知识库检索、网页搜索、网页读取可作为独立的只读动作。
- 可以根据中间结果继续查找，也可以在资料足够时停止。
- 同一次问答中的资料来源、实际送模内容和最终引用能够对应。
- 问答执行有明确的轮数、调用次数、时间和模型输入输出预算。
- 用户能看到简明的执行进度、使用的来源以及明确的完成或失败状态。
- 入库界面准确区分解析、分块、向量索引、关键词索引的状态。
- 最终使用既有知识库题目和新增联网场景，检验质量、引用、成本和停止行为。

### 不纳入本次第一版

不增加写入类工具、任意代码执行、多智能体协作、可视化工作流编辑器、通用插件市场或微服务拆分。长时后台任务、断点恢复、长期记忆没有得到需求确认，不直接加入。

保留现有登录和知识库归属校验，不把此次重构扩展成一套新的权限平台。内部工具调用仍必须遵守用户已选择且有权访问的知识库范围。

## 四、阶段总览

| 阶段 | 解决的问题 | 阶段交付物 | 依赖 |
|---|---|---|---|
| 准备阶段 | 环境、数据与关键选择尚未固定 | 数据清单、恢复依据、确定的实现约束 | 无 |
| 第一阶段 | 分数失真、筛选冲突、来源与上下文脱节 | 统一资料处理和有来源的知识库问答 | 准备阶段 |
| 第二阶段 | 模型只能输出文本，缺少只读工具执行 | 模型工具调用能力、知识库与网页工具 | 第一阶段 |
| 第三阶段 | 问答只能执行固定的一次检索与生成 | 有预算和停止条件的后端执行循环 | 第二阶段 |
| 第四阶段 | 浏览器承担编排，状态与引用展示不完整 | 统一过程事件、前端切换与引用跳转 | 第三阶段 |
| 第五阶段 | 入库完成状态与实际可用情况不完全一致 | 阶段状态、明确失败位置与定向重试 | 准备阶段，建议在第四阶段后完成 |
| 第六阶段 | 无法判断新流程是否真正改善 | 完整评测、验收记录、运行说明与清理 | 第一至第五阶段 |

第一至第四阶段贯通“提问—工具执行—带来源回答”的主流程。第五阶段完善入库状态。第六阶段统一完成效果评测和交付验收。

每阶段完成后再进入下一阶段；必要的前后端配套修改放在同一阶段，不留下调用新旧协议各一半的状态。以下文件范围是预期影响范围，具体拆分在对应阶段开始时结合代码确定。

## 五、准备阶段：固定数据和实现约束

### 主要工作

1. 核对实际 Compose 项目、端口、数据库、上传卷和源码挂载，启动后端时确认连接到已有 PostgreSQL。
2. 为存量数据库和上传原文件准备成对的备份，记录文件位置、备份时间和恢复方法；备份不提交 GitHub。
3. 记录当前文档、分块、向量和原文件对应关系。准备最终验收使用的已知资料，保存已有评测结果和当时配置；此时不重新跑完整评测。
4. 检查现有模型是否支持预期的原生工具调用、用量返回、输入容量与取消行为。不能仅凭“兼容某种聊天请求格式”认定这些能力可用。
5. 确定网页搜索和网页读取供应商、密钥配置及调用限制；具体外部只读工具需先明确用途，再接入。
6. 确定实现方式。建议先在现有 Python 项目内实现小规模执行循环；如确认必须支持会话恢复或中断续跑，再评估采用 LangGraph。实现方式只选一套，不并存两个执行引擎。
7. 确定每次提问的预算、联网触发方式、外部查询可携带的信息范围，以及是否需要逐字显示回答。
8. 创建简明术语表，记录“检索命中”“实际送模资料”“引用”“执行状态”等容易混淆的概念。只把已经确定的选择写成设计决策记录。

- deployments/docker/docker-compose.yaml
- deployments/docker/Dockerfile
- ai-service/internal/conf/config.py
- ai-service/pyproject.toml
- ai-service/.env.example
- GLOSSARY.md 与 docs/adr/，在实际确认内容时添加

### 完成标准

能明确回答“数据在哪、后端用哪个库、原文件从哪读取、采用哪个模型和搜索工具、一次执行最多消耗多少资源”。依赖和工具尚未确定时，不虚构已经完成选型。

数据备份及后续迁移只操作本项目，不调整其他项目容器。保持现有单后端进程安排；关键词索引尚未改造前不增加工作进程。

## 六、第一阶段：修复分数并统一资料处理

### 目标

先让现有知识库问答的资料可靠，再在其上添加工具循环。

### 主要工作

1. **删除按排列位置制造分数的逻辑。** 知识库问答由后端取得真实检索结果并直接传到生成步骤，避免浏览器只回传分块编号后重新构造评分。
2. 为本阶段同步调整问答页面的调用方式：问答请求直接携带问题与所选知识库范围；前端不再替生成步骤选分块。过程展示在第四阶段完善。
3. 纯检索列表可以继续提供，但不再作为生成步骤的必经前置请求；问答页面的资料列表优先复用本次问答返回的检索信息，避免相同问题重复检索。
4. **资料筛选规则只保留一个承担位置。** 清除生成模块读取检索模块私有阈值的行为，消除术语规则放行后又被另一个硬阈值删除的不一致。
5. 区分向量分、排名融合分和重排分，记录来源及计算方式。不同类型的分数不直接共用阈值；没有真实分数的来源保持无分数，不补造数值。
6. 将资料筛选、相邻分块合并、输入预算和引用对应关系放在同一资料处理模块中；内部仍可以拆成清晰的小函数。
7. 每份资料保留来源类型、原文位置及本次使用内容。合并相邻分块后保留所有参与分块编号；截断后准确记录实际送给模型的部分。
8. 根据最终选定模型计算输入长度。完整预算包括系统提示、问题、工具说明、已有执行记录和资料，并预留回答空间。现有字符数限制不能继续冒充模型实际容量。
9. 生成本次回答使用的引用编号，并保留编号到实际资料的映射；从未送给模型的资料不能被当成该回答已使用的依据。
10. 清理旧的“浏览器挑分块—后端按编号重载—合成评分”生成路径及相应请求字段、缓存与说明，不保留兼容分支。
11. 对本阶段触及的重排失败静默返回原候选等逻辑明确失败行为，不把不同分数的候选伪装为已完成重排。

### 涉及位置

- ai-service/internal/biz/retrieval.py、rag.py、entity.py、relevance.py
- ai-service/internal/biz/context_expand.py、tokenizer.py
- ai-service/internal/prompt/base.py
- ai-service/internal/service/retrieval.py、rag.py
- ai-service/api/openapi/schemas/retrieval.py、rag.py
- ai-service/internal/server/http.py
- web/src/api/search.ts、hooks/useSearch.ts、components/Search/SummaryPanel.vue
- web/src/types/search.ts、utils/searchCache.ts
- 新的资料处理模块，名称和内部文件拆分在本阶段确定

本阶段实施与检查结果见 [第一阶段完成记录](../implementation/phase-1-report.md)。当前输入长度明确使用保守估算，未声称已取得千问精确分词计量；测试与评测文件按用户规则保持不动。

### 借鉴与完成标准

借鉴 Onyx 将同一批资料同时用于模型上下文与引用映射的思路，以及 RAGFlow 对内部工具来源登记的要求。

本阶段完成时：

- 不再出现根据分块顺序合成的相关性分数。
- 检索允许进入生成的资料，不会再被另一套隐含规则重新否决。
- 回答引用能定位到实际送模片段，邻块合并和截断后仍然对应。
- 大量资料不会挤占预留回答空间；模型长度计量无法确定时明确处理，不能声称已准确计量。
- 现有资料可以继续问答，不要求全量重新嵌入。
- 浏览器与后端在同一阶段切换完成，过期生成缓存不能复用旧分数或旧来源映射。

## 七、第二阶段：接入明确的只读工具

### 目标

让模型可以请求工具调用，后端按明确规则执行，并将结果交回模型。

### 主要工作

1. 扩展现有模型调用的数据结构，明确区分“回答文本”和“工具调用请求”，保留调用编号、工具名称、参数和对应结果。
2. 按准备阶段选定的模型实现原生工具调用。若模型不支持，明确提示配置能力不足，不通过解析任意自然语言模拟调用。
3. 首批工具提供知识库检索、网页搜索和网页正文读取。其他外部只读工具在用途和来源确定后按同一方式接入。
4. 知识库检索继续复用现有向量、关键词和重排逻辑；多知识库范围由后端协调。
5. 网页搜索与正文读取分开。搜索摘要只标记为搜索摘要；未读取正文时，不能把摘要伪装为整篇网页的依据。
6. 网页结果保留 URL、标题、获取时间以及实际取得的文字；网址去重，控制每次返回数量和正文长度。
7. 集中检查工具参数、知识库访问范围、允许访问的网页范围、超时和取消。不开放写入工具和任意代码执行。
8. 外部查询只带必要的搜索信息，不自动发送整篇私有文档；允许外发的信息范围按准备阶段的决定执行。
9. 工具失败返回明确错误，不能把异常转成“没有结果”，也不自动切换另一个供应商掩盖失败。
10. 网页和工具返回的文字作为资料处理，不能据此扩大可调用工具或改变程序规定的执行限制。

### 涉及位置

- ai-service/internal/biz/repo.py、entity.py
- ai-service/internal/data/llm/ 中选定模型的实现
- ai-service/cmd/wire.py、internal/conf/config.py
- 新的只读工具执行模块与网页访问实现
- 第一阶段的资料处理模块

### 借鉴与完成标准

借鉴 Khoj 的文档搜索、网页搜索和网页读取分工；借鉴 Onyx 的集中工具执行；借鉴 GPT Researcher 的网址去重和研究范围限制。

本阶段完成时，三类首批工具可以分别调用，结果可追踪到来源；调用参数错误、无结果、超时和依赖失败可区分；内部调用不绕过已有知识库范围限制。

本阶段实施与检查结果见 [第二阶段完成记录](../implementation/phase-2-report.md)。首批三类工具与原生调用的单步能力已接通；自动问答循环见第三阶段完成记录，前端联网交互仍在第四阶段实施。

## 八、第三阶段：实现有边界的后端执行循环

### 目标

让模型根据工具结果决定下一步，而不是永远只执行一次检索后生成。

### 执行流程

```text
接收问题与允许使用的来源
        ↓
模型判断下一步动作
        ↓
执行已批准的只读工具
        ↓
保存本次实际结果和资料来源
        ↓
检查预算、重复调用与取消状态
        ↓
模型决定继续查找，或依据已有资料作答
        ↓
检查最终答案引用
        ↓
返回答案、来源与结束原因
```

知识库没有命中，只表示这次工具没有取得资料，不自动终止整次问答。允许联网时，模型可以根据问题主动选择网页工具。依赖调用失败与资料不足是两种不同情况，不把依赖故障当成自动改走网页的理由。

### 主要工作

1. 后端持有一次问答的允许范围、执行记录、资料集合、预算消耗与结束原因。
2. 支持将问题拆为必要的子查询，依据实际返回的资料继续查找；不强制每个简单问题都进行拆解或联网。
3. 对轮数、工具总调用次数、每次工具耗时和整次执行时限设置程序上限。模型不能通过连续调用绕过这些限制。
4. 对模型输入输出用量设置累计预算，每次调用前检查剩余空间，并为最后作答预留额度；实际用量与估算用量区分记录。
5. 防止重复执行相同的无新增信息查询；达到上限后以明确原因结束，不继续无界重试。
6. 删除现有“资料非空但模型拒答，就追加必须回答提示再生成”的强迫作答逻辑。资料不足时可以补查；仍不足时明确说明缺失信息。
7. 最终答案中的事实性结论附引用；引用编号必须对应本次实际送模资料。缺失或无效引用不能被当作正常完成。
8. 资料存在冲突时，保留不同来源及其时间信息，说明分歧，不仅按某个检索分数选出“真相”。
9. 记录工具动作、参数摘要、结果摘要、用量及停止原因，为最终评测准备依据；不记录或展示模型内部思维链。
10. 引用编号存在只是结构正确，不代表结论必然被资料支持。语义支撑必须进入第六阶段的质量评估，不能把格式校验当成真实性保证。

### 涉及位置

- ai-service/internal/biz/rag.py 及新的问答执行模块
- 第二阶段工具执行与第一阶段资料处理模块
- ai-service/internal/service/rag.py
- ai-service/internal/prompt/templates/rag.yaml 及工具使用提示
- 模型、运行结果和事件的数据结构

### 借鉴与完成标准

借鉴 Khoj 和 Onyx 的有上限循环；借鉴 LangGraph 示例的条件分支和资料判断；借鉴 GPT Researcher 的子问题研究；借鉴 RAGFlow 为最终回答保留预算。

至少能够检查：仅用知识库回答、需要网页补充、需要两步取证、仍无充分资料、工具失败、重复查询、达到预算、用户取消。每种情况都有明确终态，不能统统变成一段“模型回答失败”的正文。

本阶段开始记录最小执行事件，作为内部统一事实；第四阶段再完成对外传输和前端展示，不建立两套独立状态判断。

本阶段实施与检查结果见 [第三阶段完成记录](../implementation/phase-3-report.md)。有边界循环已接入同步及 SSE 问答，实际知识库回答通过；网页两步流程以固定资料检查，真实 Tavily 调用当前因容器连接失败明确结束，网络恢复后仍需补验。前端过程展示与运行资料七天保留留在第四阶段。

## 九、第四阶段：切换前端并完善进度与引用

### 目标

用户提交一次问题即可看到完整过程，浏览器只负责交互展示。

### 主要工作

1. 统一同步结果和 SSE 事件的来源，两种输出均由同一次后端执行产生，不各自重新执行一遍业务流程。
2. 对外明确表达开始、工具执行、工具完成、来源更新、回答发布和最终结束；区别失败、无充分资料、预算用尽与取消。
3. 前端展示简短阶段说明，例如“正在查知识库”“正在搜索网页”“正在读取资料”；不要求显示内部实现细节。
4. 清除浏览器端遗留的跨库编排、生成前分块挑选、无命中直接拒答以及按答案字符串判断失败的逻辑。
5. 知识库引用可打开原文片段，网页引用可打开实际使用的 URL。被截断、合并和跨轮复用的资料仍能追溯。
6. 将一次运行的来源绑定到该次运行和实际引用编号，不再只靠问题文字拼缓存键复用答案；旧缓存按数据结构版本失效。
7. 用户取消时，取消信号传到模型和工具调用，并停止后续动作；不能只在浏览器停止显示。
8. 明确选择答案发布方式。建议第一版实时推送过程状态，最终答案在引用检查后发布；这不冒充逐字流式输出。若需要逐字显示，则明确区分“生成中的草稿”和“引用检查后的最终答案”，在准备阶段选定方案后只实现该方案。
9. 记录可供最后验收回放的最小运行信息及实际资料快照。保存位置和保留期限在准备阶段确定，避免无限积累原文。
10. 断线重连与进程重启后续跑不自动加入第一版；不能因保存了运行记录就声称具备恢复执行能力。

### 涉及位置

- ai-service/internal/streaming/sse.py
- ai-service/internal/server/http.py、internal/service/rag.py
- ai-service/api/openapi/schemas/rag.py
- web/src/api/search.ts、types/search.ts、hooks/useSearch.ts
- web/src/components/Search/SummaryPanel.vue、views/SearchResults.vue
- web/src/utils/searchCache.ts
- 如确定持久化，涉及数据模型与显式数据库迁移

### 借鉴与完成标准

借鉴 Onyx 的工具边界事件、Khoj 的研究状态传递、Open Notebook 的阶段提示和来源跳转。

页面只提交一次问答任务，列表与回答来自同次运行；事件次序能解释执行结果；引用能点击到对应资料；取消后不再启动新工具；最终失败不写成一段看似正常的回答。

## 十、第五阶段：细化入库状态和定向重试

### 目标

保留上传、解析、分块、嵌入流程及已有重试，准确说明文档在哪一步完成或失败。

### 主要工作

1. 分别跟踪解析、分块、向量索引和关键词索引，给出对应错误及更新时间。
2. 将“文档处理完成”定义为当前配置所要求的步骤全部完成。若配置使用混合检索，关键词索引失败就不能标记为完整可用。
3. 保留现有嵌入失败统计和重试；只补齐缺少的阶段信息。重试时从实际失败步骤继续，避免为了修关键词索引而重新调用所有嵌入请求。
4. 启动时重建进程内关键词索引的成功与失败也要被记录；不能启动失败仅告警、界面却继续显示所有文档已经就绪。
5. 处理重新解析时，明确旧分块和索引何时被替换、失败后文档是什么状态，避免使用过期引用。工具执行中的资料快照保留其当时实际内容。
6. 前端显示“解析完成、索引失败”等真实情况及对应重试入口，避免只显示笼统“成功”。
7. 为新增状态设计显式迁移与存量回填。现有 29 篇文档的状态根据真实索引情况计算，不凭旧状态统一标记成功。
8. 不修改既有向量模型或维度，不默认重建全部向量。状态细化不等于引入任务队列、独立工作进程或新的入库平台。

### 涉及位置

- ai-service/internal/biz/document.py、chunk.py、embedding.py、constants.py
- ai-service/internal/data/models.py 及文档、分块持久化实现
- ai-service/cmd/migrate.py 与新增显式迁移
- ai-service/internal/server/http.py 中索引启动逻辑
- ai-service/internal/service/document.py、api/openapi/schemas/document.py
- web/src/views/Document.vue、DocumentDetail.vue 及文档类型、调用和展示文件

### 完成标准

失败步骤清楚可见，针对失败步骤的重试可以完成修复；关键词索引缺失不会被当作完整成功；进程重启后就绪状态能重新核实；现有文档与原文件保持对应。

这一阶段主要源于本项目代码中的状态问题，不把其他项目的入库实现误称为已经核查过的可复制方案。

## 十一、第六阶段：完整评估、验收与交付

### 目标

回答三个问题：答得是否正确，依据是否真实，执行代价是否可接受。

### 主要工作

1. 保留现有黄金题集作为知识库限定场景。原来的“资料无答案应拒答”标准，只用于不允许联网的题目。
2. 新增允许联网的场景，明确哪些需要网页、哪些需要跨来源取证，以及哪些即使联网也应说明资料不足。
3. 评估直接读取实际运行记录和实际送模资料，不再在评测脚本中另行扩邻块、重建一份可能不同的证据。
4. 知识库来源以文档版本和实际片段核对；网页来源以本次抓取时间、URL 和保存的实际内容核对，避免第二天网页变化后无法解释结果。
5. 保留现有召回率、排名和拒答指标，同时区分纯检索质量与最终回答质量。
6. 增加引用有效性、结论支撑情况、来源覆盖、工具选择、重复调用、停止原因、耗时和模型用量记录。
7. 原有关键词与文本重合规则继续作为辅助，不把它们当成“所有结论都真实”的唯一证明。多来源、引用错配和冲突案例需人工核对。
8. 设置正常、资料不足、工具失败、超时、取消、预算用尽、无效引用和旧缓存场景；不只检查最终是否出现一段文字。
9. 完成现有相关检查、前端构建、Docker 镜像构建、数据库迁移和实际页面操作的联合验收。此前各阶段只做直接相关的检查，不反复运行全量评测消耗接口额度。
10. 使用已保存结果进行离线重评分时，不应重新检索或调用模型。修正现有“重评分仍先走检索和资料构造”的路径后再承诺此能力。
11. 测试与评测文件的新增或修改单独列明；本计划书不提前创建或修改测试。第六阶段按用户已确认的评测范围实施，不以“临时验证”为理由改动评分标准。
12. 清除废弃生成路径、未使用字段、旧提示和失效依赖，更新运行说明。全部 Python 环境、依赖和镜像内安装流程统一使用 uv，修正现有镜像使用 pip 的方式。

### 验收记录

| 验收项 | 要保存的证据 |
|---|---|
| 原有知识库能力 | 与同一题集、同一资料条件下的已有结果对照 |
| 网页与外部工具 | 实际调用及实际返回资料，不只保存搜索词 |
| 来源准确 | 回答引用与实际送模片段对应，抽查结论是否被支持 |
| 输入与执行预算 | 配置上限、实际消耗、达到上限后的结束记录 |
| 状态与取消 | 页面、后端记录和终态一致 |
| 入库完整性 | 现有数据迁移后核对，失败阶段与重试结果准确 |
| 部署与启动 | Docker 构建、启动、就绪、原文件访问及索引重建情况 |
| 代码卫生 | 文件编码与换行检查、git diff --check、废弃实现清理 |

硬性通过条件包括：没有合成相关性分数；没有无效来源被标记成有效引用；达到配置预算后不再启动新动作；存量资料保持可访问；工具失败与空结果可区分。

答案正确率、延迟和费用的数值目标，在准备阶段依据现有结果与可接受成本确定。不能在没有对照结果时承诺任意百分比提升，也不能为了通过验收放宽指标。

4. 新增文本为 UTF-8 无 BOM、LF；修改旧文件保留原编码和换行，交付前检查 git diff --check。

6. 不因“使用 Docker”就另建一套数据，也不因重构就删除、替换现有持久卷。
7. 数据结构变更通过明确迁移完成，不在普通请求中悄悄修改表结构。
8. 不将调研建议当成已经批准的供应商、预算和框架选择；涉及必要选择时先核查，再按本计划标记的待定事项确认。
9. 开发阶段的运行检查与最终效果评估分开；不在每个阶段重复执行完整题集。
